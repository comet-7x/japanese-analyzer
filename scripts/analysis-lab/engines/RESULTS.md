# 本地解析引擎交叉验证与选型

> 后续接入记录：同版本 Sudachi 0.7.0 已通过自有 WASM 包装接入网页的可选
> 「本地解析」，默认仍为模型解析。76 个输入与原生参考输出逐字段一致；
> Chrome 155 和 WebKit 27.2 已通过长文、缓存、停止校正和手机布局测试。
> 见 [使用与构建说明](../../../docs/local-analysis.md) 及
> [WASM 验证记录](../results/sudachi-wasm.json)、[浏览器记录](../results/sudachi-web.json)。
> 下文保留最初选型测试的结果和当时尚未完成的边界；真实模型校正速度与语言质量仍未验证。

实测日期：2026-10-16。机器：Apple M5 Pro / macOS arm64。
Node 22.23.3、CPython 3.12.13、Chrome 155.0.8059.80。

**选定 Sudachi.rs 0.7.0＋SudachiDict Core 20261015＋A 模式，作为下一阶段「本地初稿＋模型校正」实验的主选。**
Lindera 6.2.0＋IPADIC 保留为偏重 Node 接入与内存开销的备选。
本次选择没有改变生产默认解析，也没有把已有 kuromoji 对照实验改写成新引擎。

## 实测结果

每个配置三个独立进程串行运行；每个进程对相同长文执行 50 次热运行。
长文就是四季文章的 fixture，包含文件末尾换行，共 447 个 UTF-16 码元。
下表为中位数。初始化包含引擎加载与词典初始化，未清空操作系统文件缓存；
热运行包含分词和通用字段提取，不包含共享学校文法转换，也没有任何模型调用。
RSS 是完成相同测试负载后的整个进程内存，包含 Node 或 Python 运行时，不能视为引擎独占内存。

共享学校文法转换在各配置上的长文中位数约 0.06–0.12 ms，单独记录于 JSON。
Vaporetto Python 绑定为 0.3.3，底层 Rust 0.6.5，模型发布版 v0.5.0。
Sudachi 和 MeCab 的数字包含 Python 绑定，尚不能当作直接 Rust 或 C++ 接入的实际性能。

“基础固定用例”同时要求切分、项目约定的学校词性和注音一致；“额外注音目标”
在另 19 个句子上检查 21 个原文范围的完整注音，允许跨词项拼接，避免粒度差异
直接决定得分。它们都是小型人工固定预期，**不能解释为日语总体准确率**。
「私」接受「わたし／わたくし」，「明日」「昨日」也接受标准读法变体；
「人気のない道」不作为唯一答案评分。严格 canonical 分数也保留在 JSON。

## 交叉验证证明了什么

- 十三个配置在每个独立进程的 76 个输入上都能经适配严格还原原文。
  其中包括 17 个完整性压力用例、30 个基础质量用例和额外读音/观察输入。
- 三个独立进程的输出一致；本轮单句与合并质量输入没有出现差异。
  四季长文按生产句界切分后，与整篇解析的结果也一致。
- kuromoji、Lindera 原生 IPADIC、Lindera WASM IPADIC、MeCab IPADIC 在
  30 个基础用例和四季长文上的学校化结果完全一致。这支持“换相同词典的引擎
  不会自动改善这里的读音问题”，不代表这些共同结果全部正确。
- 浏览器另测 kuromoji、Lindera WASM/IPADIC、Lindera WASM/UniDic，各启动
  三个独立的真实 Chrome；每次 76 个输入均与 Node 参考输出一致。

Chrome 通过本机 HTTP 加载时，初始化中位数分别为 458.0、57.6、140.4 ms；
长文热运行中位数分别为约 1.2、0.8、1.1 ms。WASM 线性内存分别为
IPADIC 92.625 MiB、UniDic 382.125 MiB；这不是浏览器整个进程的 RSS。
本机加载不能外推到真实网络的首次下载时间。

## 对选型有影响的差异

1. **IPADIC 换引擎，资源开销改善，读音问题仍在。**
   例如「一人」仍分成「一／人」，注音拼成「いちにん」；
   「令和」的注音拼成「りょうわ」；AI、ChatGPT 缺少读音。
   Lindera 是很好的运行时替代，但本轮没有提升这部分语言质量。
2. **Sudachi Core 对这组词汇的覆盖更合适。**
   能提供「一人／ひとり」「令和／れいわ」及 AI、ChatGPT 的读音。
   Small 体积与内存较小，但本轮少通过一个现代词汇读音目标。
   Core 在质量、资源开销和现代词汇覆盖之间更符合当前学习工具的需求。
3. **MeCab＋UniDic-lite 是有竞争力的质量/内存备选。**
   本轮同样 17/21，而且「十日」能给出「とおか」；但 AI、ChatGPT
   缺读音。采用它需要解决应用的原生绑定与跨平台分发，当前实测只覆盖 Python 绑定。
   本次不因其初始化略快或 RSS 更低就忽略词汇覆盖差异。
4. **Vaporetto 值得保留研究，但本配置不作为默认初稿。**
   假名模型的读音目标最好，也能给出「一日中／いちにちじゅう」；
   但初始化约 2.1 秒、进程 RSS 约 1.1 GiB，基础约定还有三个用例不匹配。
   这只是本模型/绑定配置的结果，不代表所有 Vaporetto 模型的资源开销。
5. **UniDic 版本和字段不能混为一谈。**
   Lindera 本次预编译 UniDic 缺少现代 surface-kana 字段，使用表层发音回退后
   会出现「学生／ガクセー」「東京／トーキョー」，不满足项目的标准假名注音。
   这不是证明 UniDic 本身较差；MeCab＋UniDic-lite 的对照已经显示两者的区别。

## 已知边界与采用方式

选择 **A 模式**是为了先提供较细的结构给学习界面和模型校正。B/C 在这组基础
评分里没有优势，C 会把「選挙管理委員会」等合成更长词项。A 也不天然等于学校文法；
形容动词、助动词和补助动词仍须转换与校正，当前共享转换只覆盖一小部分规则。

推荐下一阶段保持「本地初稿＋完整上下文模型校正」。本地原文覆盖成功不等于
语言正确：Sudachi 本轮仍未满足「十日」「二十日」「四月一日」「一日中」四个
注音目标。例如「十日」给出「とうか」，而固定标准假名预期为「とおか」。
不应通过放宽原文校验或把发音长音机械替换为假名来掩盖差异。

适配时还需处理 Sudachi 的规范化展开：`…` 和 `㍿` 会产生后续零宽原文词项。
实验桥接仅在原文范围连续时将续项及读音合回拥有原文的前项；最终仍严格检查
原文拼接。该逻辑不改写原文，也没有进入生产路径。

**生产采用前还缺少以下证据，因而本次没有切换默认实现：**

- 同版本 Sudachi 的 Rust/Node 接口或 sidecar，以及桌面各目标平台的打包验证。
  不建议仅为这个功能把本轮的 Python 测试运行时装进应用。
- 同版本浏览器 WASM 与 Core 词典的加载、内存和结果验证。
  本次真实浏览器实测覆盖的是 Lindera 和 kuromoji，**没有验证 Sudachi 浏览器路径**。
  检查到的社区 WASM 封装使用其自己的 0.6.11 系列分支，不能直接假定与本轮
  官方 0.7.0 / V1 格式 20261015 词典兼容。
- 更广的独立人工标注学校文法/语境读音语料，以及相同模型配置下的本地＋模型
  与纯模型端到端对比。本轮全是本地测试，不能证明模型校正更快或已经稳定。
